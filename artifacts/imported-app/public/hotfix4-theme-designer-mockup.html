Why we don't try to "wire" the highlight-color picker
Amber is the brand accent across the entire app — license button gradients, mic-active pills, NDI badge tints, recording indicators, license-trial banners, bible-downloads warnings, all use literal Tailwind classes like bg-amber-500/20, text-amber-300, border-amber-500/40, ring-amber-500/30. Tailwind classes are static strings that get compiled at build time — they can't take a runtime variable. "Wiring" highlightColor would require:
  • Defining 6 color×6 alpha×4 property maps (color/bg/border/ring) in Tailwind safelist
  • Touching ~50 files to swap hardcoded amber for dynamic class lookup
  • Risk: re-coloring elements the operator does NOT want re-colored (license button, mic indicator)
Not a hotfix. This was scope creep from a feature that was never actually built — the original v0.5.52 commit added the picker UI but never wrote the consumer. Cleanest move: remove the dead picker. If operator one day wants a "brand color" feature, we scope it as its own ship.
