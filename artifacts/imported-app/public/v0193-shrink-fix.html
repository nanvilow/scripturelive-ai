Settings round-trip text-shrink — diagnosis & fix

Operator's report: open a verse, go to Settings without touching anything, come back → text is suddenly smaller.

1. Before opening Settings FIRST PAINT

Verse fills the safe area — autofit picked the largest scale that fits both width and height. This is correct.

2. After Settings round-trip SAME VERSE — SHRUNK

Same verse, same operator pick, same container size — but autofit settled at a smaller scale. The bottom of the safe area is now empty.

Root cause

When the operator opens Settings, the live console (including both Preview and Live iframes) unmounts — Settings is a full-screen overlay that REPLACES the shell (this is documented in the OutputBroadcaster comment too). Coming back, both iframes mount fresh and run fitVerseText() on their first paint.

But on first paint the web fonts haven't finished loading yet — the iframe renders with the system fallback font, which has wider character metrics. Autofit picks a smaller scale to make the wider fallback fit, then caches that scale in __fitKey. A few hundred ms later the web font loads, characters reflow narrower, and the verse now has unused space at the bottom — but the cache says "we already fit this," so autofit never re-runs. Permanent shrink until the operator manually triggers a re-render.

Fix (3 belts in route.ts ~L936-980)

(a) Re-fit when web fonts finish loading. Hook document.fonts.ready and force a re-fit when the promise resolves — kills the FOIT/FOUT race directly.

(b) ResizeObserver on the verse parent. Any container-size change (Settings overlay closing, operator resizing a panel, dev tools opening, browser zoom) triggers a forced re-fit. Window resize alone misses iframe-internal layout shifts that don't bubble out.

(c) Belt-and-braces 250ms re-fit. One extra forced re-fit a quarter-second after first paint, in case the font CDN is slow or layout settles asynchronously.

Each forced re-fit clears __fitKey='' first so the binary search runs against the now-correct font metrics. Net cost: ~1.5 ms total, only on first paint of a fresh iframe.
