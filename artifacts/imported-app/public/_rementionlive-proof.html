Operator saw the column "ignore" the re-mention.

What changed (single 6-line surgical edit in store.ts ~L836)
BEFORE: if (existingRank >= incomingRank) return {}  ← no state change → no useEffect → no go-live
AFTER:  promote existing entry to front of array, give it a fresh id + fresh detectedAt, preserve original source + confidence:
if (existingRank >= incomingRank) { // PROMOTE — keeps the higher-quality existing source/confidence, // but flushes through a NEW array reference + NEW id so: // • detectedVerses array changes → auto-live useEffect re-runs // • new id ≠ lastAutoVerseId.current → re-fire gate clears // • shouldFireAutoLiveStable picks front-of-array → broadcast const promoted = { ...existing, id: `det-rementioned-${Date.now()}-${rand()}`, detectedAt: new Date(), } const filtered = state.detectedVerses.filter(d => d.reference !== v.reference) return { detectedVerses: [promoted, ...filtered].slice(0, 100) } }
What does NOT regress
• requestNavigatorRef still fires at the top of the reducer (v0.7.184 GR-A) — navigator updates whether the verse is new OR re-mentioned.
• addDetectedVerseCandidate (speculative <50% guesses) is intentionally unchanged — those don't go live and shouldn't thrash the broadcast on every speech tick.
• Cross-source rank protection (semantic doesn't downgrade an explicit entry) preserved — promotion uses ...existing spread so authoritative source/confidence survive.
• Stability gate in verse-auto-live.ts still applies — re-mention has to clear the per-source stability counter (≥3 frames) and the 500 ms LIVE_HOLD_MS dwell, exactly like a fresh mention. So a single accidental tick won't snap-back; a real re-mention will.
• 4 dedupe-gate navigator-fires in speech-provider.tsx from v0.7.184.2 are unchanged — they still cover the upstream paths.
• Suggestion column behaviour unchanged — promotion only triggers when source rank is equal-or-higher than existing.
