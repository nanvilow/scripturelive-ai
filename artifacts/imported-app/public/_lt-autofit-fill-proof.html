ROOT CAUSE — one line
Old fitVerseText only ever shrunk the verse (k clamped to [0.60, 1.00]). What changed in the math
Old logic (one calculation): k = (avail / actual) × 0.98 → clamp [0.60, 1.00] → if k ≥ 1, do nothing. Result: short verses never grow.
New logic (binary search, 10 iterations): test fontSize = baseSize × mid for mid ∈ [0.60, MAX]; mid is feasible iff scrollHeight ≤ avail × 0.98 AND scrollWidth ≤ availW. Largest feasible mid wins.
MAX = 2.50 when parent.closest('.lt-content') matches (LT branch); 1.00 otherwise (fullscreen — same shrink-only behaviour as before, no balloon for short verses on the main display).

Why binary search on font-size (not transform: scale)

transform: scale(k) scales the painted box but NOT the layout box. At k > 1, the visual width = clientWidth × k, which spills horizontally OUT of the LT bar and gets clipped by overflow:hidden. So transform-scale can shrink correctly but cannot grow correctly. font-size: baseSize × k changes the layout box — the wrap re-flows inside parent.clientWidth at the new size. Both height AND width constraints are honoured naturally by the search test: if (p.scrollHeight <= avail*0.98 && p.scrollWidth <= clientWidth) feasible Cost: 10 iterations × ~0.05 ms layout = ~0.5 ms per verse change. Cached on (textLength|width×height) — re-renders at the same key re-apply the cached pixel size with zero search cost.

Bounds rationale (why 0.60 floor / 2.50 ceiling)
Floor 0.60 — kept identical to v0.7.183 GR-B (operator-explicit; lowering it caused "not even small" regression on pathologically long verses).
Ceiling 2.50 — fits the longest single-word verse name "begotten" at 2.5× the CSS base in a 22%-tall LT bar at 1920×1080 without overflow at typical bar height (250px → font-size ≈ 230px max would touch the top; binary search lands well below the ceiling for any verse with multiple words). Higher ceilings risk monolithic single-letter blow-ups on 1-word verses; lower ceilings prevent "Jesus wept." from filling.
