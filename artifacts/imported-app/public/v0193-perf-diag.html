Why some videos lag — diagnosis

Same MP4 ends up decoded 4–6 times in parallel. Your GPU's hardware video decoder typically supports 2–4 concurrent streams. The 5th+ falls back to software decode on the CPU → that's where the stutter comes from.

Proposed fixes (4 surgical changes)

  • 1. Unmount Preview's video element when the same media is on Live. Biggest win
    The Preview pane already auto-pauses (we just shipped that). Going one step further — replacing it with a static "ON AIR" card while Live owns the clip — frees an entire decoder. Operator gets the Preview back the moment they Stop Live or move to a different slide.
  • 2. Don't run the Web Audio analyser on muted surfaces. Medium
    Preview's level meter doesn't need to decode audio samples when its speaker icon is off. Same for NDI capture (always silent). The meter just shows "0" — a Web Audio analyser per surface costs a few % CPU each that we don't need to spend.
  • 3. Loosen output drift threshold from 0.12s back to 0.20s. Medium
    The 0.12s I shipped in hotfix.2 was too aggressive on slower machines — the renderer was seeking every couple of seconds, and each seek causes a tiny stutter. 0.20s still keeps the output close to your Live Display (humans don't notice <250ms drift in non-music video), but cuts the seek frequency dramatically.
  • 4. Don't mount the in-app NDI preview iframe unless the NDI panel is open. Medium
    Right now that little NDI preview panel runs full-time even when collapsed, decoding the same clip in the background. Mount it only while the operator has the panel expanded.
What this WON'T do: if a single 4K clip is too heavy for your machine to decode at all (rare on the desktop you're using, but possible for very high-bitrate files), no amount of decoder-count reduction will help. Best case for those: re-encode them to 1080p H.264. I'll add a one-click "Optimize for ScriptureLive" button later if needed — separate task.
