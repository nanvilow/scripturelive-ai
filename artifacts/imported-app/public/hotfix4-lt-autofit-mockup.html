v0.7.194-hotfix.4 — Lower-Third autofit race fix on mode switch

Symptom: flipping NDI Display Mode → "Lower Third" leaves the Bible text overflowing/disorganised. Dragging the Lower-third size slider by even one tick makes it snap to fit. Root cause: autofit measures the freshly-built .lt-box one rAF too early — its container-type:size + CSS clamp(... cqw, ... cqh ...) font-size hasn't resolved yet on first rAF. Slider drags trigger a SECOND DOM rebuild that measures a now-settled box, which is why dragging "fixes" it.

What happens on every mode switch (today, broken)

FRAME 0 Operator clicks LOWER THIRD. ndiDisplayMode='lower-third' writes to store → SSE push → renderer receives new state.
FRAME 1 (≈16ms) settingsRenderKey changes → cache miss → $('output').innerHTML rebuilt as .lt-box with container-type:size.
FRAME 2 (rAF fires) requestAnimationFrame(fitVerseText) runs. getComputedStyle(p).fontSize reads the CSS clamp BEFORE container-query units resolve → wrong baseline → binary search picks wrong scale → text overflows or shrinks weirdly. Cache lock fires → wrong scale becomes the cached value.
FRAME 3+ Layout finally settles but autofit doesn't run again. Text stays broken. Operator drags scale slider → rebuilds DOM → fresh measurement on a now-settled container → text snaps to fit.

What happens after the fix

FRAME 0 Operator clicks LOWER THIRD. SSE pushes new state.
FRAME 1 DOM rebuilt as .lt-box.
FRAME 2 (1st rAF) fitVerseText() runs. May still measure wrong — that's OK. Cache key now holds a tentative value.
FRAME 3 (2nd rAF + 120ms force) Container-query units are now resolved. Cache key is cleared (__fitKey='') and fitVerseText() re-runs with correct measurements. Text fits perfectly. No operator intervention.

BEFORE — single rAF, races container-query layout

One frame isn't always enough for container-type:size + cqw/cqh in a freshly-injected subtree.
// route.ts L1686-1691
// v0.7.182 — fire autofit AFTER layout settles. rAF guarantees the
// browser has run layout for the freshly-injected innerHTML before
// we measure scrollHeight. Fallback to setTimeout(0) keeps the
// call ordering identical when rAF is unavailable (extremely old
// Electron / SSR test).
if(typeof requestAnimationFrame==='function'){
  requestAnimationFrame(fitVerseText);
}else{
  setTimeout(fitVerseText,0);
}

AFTER — double-rAF + 120ms belt-and-suspenders re-fit

First rAF keeps perceived latency identical for normal slide changes. Second rAF + 120ms force-refit clears the cache and re-measures, catching the LT mode-switch race without slowing anything else down.
// route.ts L1686-1691 (replaces single rAF)
// v0.7.194-hotfix.4 — Double-pass autofit. Single rAF was racing
// container-query unit resolution on .lt-box (container-type:size +
// font-size clamp using cqw/cqh) when switching Full → Lower Third.
// First pass measures whatever's ready; second pass (rAF + 120ms)
// clears the cache and re-measures against the now-settled container.
// For normal slide changes the second pass hits the cache short-circuit
// at L862 (__fitKey match) and exits in <0.01ms — zero perf cost.
function runAutofitTwice(){
  fitVerseText();
  if(typeof requestAnimationFrame==='function'){
    requestAnimationFrame(function(){
      __fitKey=''; // force fresh measurement
      fitVerseText();
    });
  }
  // belt-and-suspenders for slow Electron offscreen layout
  setTimeout(function(){ __fitKey=''; fitVerseText(); }, 120);
}
if(typeof requestAnimationFrame==='function'){
  requestAnimationFrame(runAutofitTwice);
}else{
  setTimeout(runAutofitTwice,0);
}

Why this is safe (not a destroy-the-app change)

Normal slide change:2nd pass hits __fitKey cache → exits <0.01ms. Zero visible cost.
Mode flip (Full→LT, LT→Full):2nd pass clears cache → re-measures → correct fit.
Style-only SSE tick:Cache key matches → both passes short-circuit.
NDI capture surface:Same code path. Operator's installed NDI capture window benefits identically.
Secondary screen / projector:No container-query units there (no cqw/cqh in full-screen branch) so race never happens, but the double-pass costs nothing on cache hit.
Slider drags (scale, height):Already trigger a rebuild via settingsRenderKey, which now also benefits from double-pass — slider becomes even more responsive.
Files touched:1 (route.ts), ~12 lines
Risk:Lowest possible — additive only. Worst case 2nd pass is a no-op.

Why dragging the slider "fixed" it (confirms diagnosis)

The Lower-third size slider writes ndiLowerThirdScale to the store. settingsRenderKey() at L478 includes ndLtSc, so any change to scale triggers a fresh cache key → fresh DOM rebuild. By the time the operator's drag fires, the .lt-box from the original mode switch has been sitting in the DOM for ≥500ms — container-query units are fully resolved, so the rebuild's single rAF measures correctly and the autofit produces the right scale. That's why screenshots 2 → 3 show the text snapping to fit after barely touching the slider.

The fix removes the requirement that the operator perform that manual "kick." The 120ms force-refit IS the kick, fired automatically right after every render.
Net change: 1 file (route.ts L1686-1691), ~12 lines. Replaces single-rAF autofit kick with double-pass (rAF + rAF + 120ms force-refit). Mode-switch overflow disappears; normal slide changes incur zero perceptible cost (cache short-circuit on 2nd pass).
