# Imported App

A Next.js application providing scripture-related services for web and desktop, enhancing live service experiences, and streamlining administrative tasks.

## User preferences

-   **Autonomy**: Act without asking for consent on routine decisions — always do what's better for the app. Do not ask permission for housekeeping (file trims, refactors, retry logic, dependency bumps, replit.md trims, etc.). Only ask when a decision is genuinely destructive or shapes product direction.
-   **replit.md upkeep**: Roll the changelog window proactively. When shipping a new release entry, demote the oldest "Recent (full detail)" item to a one-line guard-rail in the same pass — do NOT wait to be asked.

## Run & Operate

-   **Install dependencies**: `pnpm install`
-   **Run dev server**: `pnpm dev`
-   **Build app**: `pnpm build`
-   **Typecheck**: `pnpm typecheck`
-   **Codegen**: `pnpm codegen` (for API client)
-   **DB Push**: `pnpm db:push` (for Drizzle schema migrations)
-   **Required Env Vars**: `MAIL_HOST`, `MAIL_USER`, `MAIL_PASS`, `MAIL_FROM`, `SMS_API_KEY`, `SMS_SENDER`

## Sandbox quirks (Replit main agent)

-   **`pnpm install` is blocked** in the main-agent sandbox — pnpm touches `.git/config` and the sandbox classifies it as a destructive git op. To restore a missing `node_modules/@workspace/<lib>` symlink, recreate it manually with `ln -s ../../../../lib/<name> artifacts/imported-app/node_modules/@workspace/<name>`. The `strip:workspace-symlinks` script (run by `pnpm run package*` to flatten symlinks for electron-builder) is a one-way trapdoor in this sandbox — re-running `pnpm install` to restore them isn't possible from here.

### Recent (full detail)

-   **v0.7.227 — Operator-controlled background brightness slider + single-click video poster preview**: TWO operator escalations addressed in one release, both in the `imported-app` artifact, both preserving prior v0.7.22x guard-rails by construction rather than by re-stating them.

    **Part A — brightness slider** (replaces the hardcoded v0.7.226 `.85` opacity / `.05` scrim pair with a user-controlled value): Operator on v0.7.226 said "I want to dial this myself for different rooms." Adding a single source-of-truth slider also satisfies the v0.7.226 PROCESS GR ("for subjective brightness complaints, do not blind-ship a guess") by making the value operator-controllable. **Files (4)**: (1) `src/lib/store.ts` — added `bgBrightness?: number` to `AppSettings` (optional for back-compat — pre-v0.7.227 persisted state has no key, renderer falls back to `85`), default `85` in `defaultSettings`. (2) `src/lib/output-payload.ts` — `settingsBlock` propagates `bgBrightness` over SSE to every output surface. (3) `src/app/api/output/congregation/route.ts` — five hardcoded literals (the v0.7.226 5-site set) replaced with CSS variable references: `.bg-image` and `#bgLayer > video, #bgLayer > img` use `opacity:var(--bg-opacity,.85)`; `.bg-overlay` and `.lt-box .lt-bg-overlay` use `rgba(0,0,0,var(--bg-scrim,.05))`; `.lt-box .lt-bg` uses `opacity:var(--bg-opacity,.85)`. New 14-line block in `applyRender(s)` writes both CSS vars to `document.documentElement` from `s.settings.bgBrightness` using the mapping `opacity = clamp(0,1,bb/100)` and `scrim = max(0, (1-opacity) * 0.333)`. Mapping chosen so brightness=85 reproduces v0.7.226 exactly (`.85 / .05`). (4) `src/components/views/settings.tsx` — `<input type="range" min={10} max={100}>` plus Dim/Default(85%)/Brightest preset buttons inside the Custom Background card, rendered only when `settings.customBackground` is truthy (no UI noise on first run). **Guard-rails preserved by construction (no inline restatement needed)**: the v0.7.226 pair invariant (opacity + scrim alpha move together on the SAME surface) is now structurally impossible to break — both vars derive from one slider value. The v0.7.226 3-surface lockstep (`.bg-image` / `#bgLayer` / `.lt-box .lt-bg` share the same numeric values) is also structural — all three surfaces read the same `:root` CSS vars. The v0.7.226 WCAG GR (body verse `text-shadow` stack stays at opacity ≥ .85) still applies; the slider's `min={10}` keeps the operator inside the band where text-shadow is the WCAG-AA fallback. **GUARD-RAIL (var fallback baseline)**: the `var(--bg-opacity, .85)` and `var(--bg-scrim, .05)` fallbacks MUST stay at the v0.7.226 baseline so first-paint (before SSE settles) AND pre-v0.7.227 persisted state render identically to v0.7.226 — changing either fallback silently shifts every first-frame render and every legacy install. **GUARD-RAIL (mapping)**: scrim derivation MUST stay `(1 - opacity) * 0.333` — this is the constant that makes brightness=85 land EXACTLY on `.85/.05` (i.e. operator-pick baseline). Any other constant breaks back-compat by drifting the v0.7.226 visual baseline. **GUARD-RAIL (slider floor)**: `min` MUST stay ≥ 10 — 0 hides the bg entirely (use the Delete button) and very-low values produce confusingly-dim output operators report as "broken". **PROCESS GR — when shipping a "make this knob operator-controllable" follow-up to a v0.7.226-style operator-picked constant, the default value MUST reproduce the picked constant byte-identically, the fallback in every render site MUST be the picked constant too, and the mapping function MUST be chosen so the default value lands on the picked constant**: anything else creates a v0.7.227-to-v0.7.226 visual diff that operators see as a regression even when they never touched the new slider.

    **Part B — single-click video shows poster frame instead of black STANDBY placard** (operator UX escalation following v0.7.222): Operator on v0.7.226 said "single-click on video in media doesn't work" — screenshots showed v0.7.222's black text-only STANDBY placard with the "Standby · Live is on air · Press Play to monitor" copy. Operator perception: "I clicked something and the preview went blank — single-click is broken." The v0.7.222 placard correctly prevented HW-decoder contention with LIVE (a 2nd `<video>` mount would steal a decoder slot from the live decoder on low-end Windows GPUs and stall the $1600 customer's live output) but the chosen UX (zero `<video>` mount → black box + text) was rejected by operators because they had no visual confirmation of which clip they just clicked. **Fix** (`src/components/layout/logos-shell.tsx` L1372-1442, the `previewStandbyForLive` branch inside the PreviewCard `<MediaVideoSurface>` slot): replaced the placard `<div>` with a real `<video>` element using the proven v0.7.225 freezeBg pattern — `preload="auto"`, `muted`, `playsInline`, `disablePictureInPicture`, `disableRemotePlayback`, NO `autoplay`. `onLoadedData` handler kicks `v.play().then(() => v.pause()).catch(() => v.pause())` to force the first decoded frame onto the compositor then immediately release the HW decoder slot. `onPlay` handler runs `setTimeout(() => v.pause(), 0)` (async, never sync) so the loadeddata-triggered `play().then(pause)` resolves cleanly without racing into AbortError spam. `key={previewSlide.mediaUrl}` forces a clean remount when the operator single-clicks a DIFFERENT tile. The Standby pill (top-left amber badge) and "Play preview" button (bottom CTA, flips `previewMediaPaused=false` to mount the full `MediaVideoSurface` with audio + scrub) now sit as overlays on top of the poster frame with `pointer-events-none` on the badge and a from-black/85 gradient backing the CTA strip so the labels stay readable against any frame content. **GUARD-RAIL (v0.7.222 lineage)**: the inline `<video>` MUST stay `muted`, MUST NOT autoplay, MUST NOT loop, MUST set `preload="auto"`, MUST execute `play().then(pause)` exactly once on `loadeddata` (NOT on `loadedmetadata` — metadata fires before any decoded frame, no first-frame paint), AND `onPlay` MUST schedule its pause via `setTimeout(_, 0)`. Synchronous pause inside the play listener races the loadeddata kick and emits AbortError spam (same trap v0.7.225 hit on freezeBg). Removing any of these re-opens either the v0.7.222 live-stall regression (operator's live video freezes the moment the new poster fires steady-state decode) OR the v0.7.225 AbortError-spam regression (browser DevTools console fills with rejected-play exceptions, masking real errors). **GUARD-RAIL (placard semantics)**: the Standby badge + "Play preview" CTA MUST stay visible — operators need to know the poster is NOT actively decoding and that pressing Play activates the dual-decoder path (operator opt-in to the contention risk). Removing the CTA leaves no path forward from standby; removing the badge confuses operators who don't realise the poster is paused. **GUARD-RAIL (gate predicate unchanged)**: the v0.7.222 `previewStandbyForLive` 5-condition AND gate (preview is media-video + previewMediaUrl truthy + liveIsMediaVideo + liveSlide.mediaUrl ≠ previewSlide.mediaUrl + previewMediaPaused) MUST stay intact. v0.7.227 only changes what's RENDERED inside the gate, not when the gate engages. The v0.7.222 Fix #8 fallback for legacy persisted slides (`isVideoUrl()` extension probe when `mediaKind` is missing) stays in `liveIsMediaVideo` upstream. **PROCESS GR — when an operator says "single-click doesn't work" and the screenshot shows a black box with text, the symptom is "no visual confirmation of what I clicked"**: a text-only placard is never the right answer for media tiles even when the underlying decoder-contention concern is legitimate. The freezeBg pattern (paint one frame, release decoder) gives visual confirmation WITHOUT the steady-state decoder cost that the gate exists to prevent. Future "show paused media preview without holding a decoder slot" patterns MUST use this play().then(pause)+async-pause idiom; preload='metadata' (v0.7.225 trap) and preload='none' (v0.7.222 trap on this surface specifically) both fail. **Tests**: same 670/670 PASS baseline as v0.7.226 (no new automated test — the v0.7.222 gate predicate tests still pass; the inside-the-gate render change is operator-visual). `tsc --noEmit` clean. NDI runtime + HW decoder slot contention still untestable in Replit — operator field validation closes the loop.
